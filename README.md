# Сайт студии звукозаписи «Фрозен Рекордс» (Казань)

Сайт-визитка с онлайн-записью по свободным слотам. Чистый PHP 8.x + SQLite,
без фреймворков и сборщиков. Правила проекта — в [CLAUDE.md](CLAUDE.md).

Боевой адрес: <https://frozenrecords.tw1.ru> (хостинг Timeweb, сервер vh470).

## Структура

```text
public_html/            корень сайта (webroot)
  index.php             главная
  booking/              онлайн-запись
  api/                  slots.php (GET), book.php (POST)
  admin/                служебная админка (вход по паролю)
  assets/               css, js, локальные шрифты, изображения
  privacy.html          политика ПДн (ЧЕРНОВИК — нужна проверка юристом)
  consent.html          согласие на обработку ПДн (ЧЕРНОВИК)
  rules.html            правила оказания услуг (ЧЕРНОВИК)
  .htaccess             HTTPS, CSP и другие заголовки, запреты доступа
  app/                  СЛУЖЕБНЫЙ каталог, закрыт от HTTP (403)
    .htaccess           Require all denied
    .env                секреты (в git не попадает)
    .env.example        образец конфига с комментариями
    includes/           конфиг, БД, SMTP, уведомления, шаблоны
    scripts/            обслуживание и выкладка
    data/               SQLite-база, логи, очередь писем
media_site/             исходные фото и логотипы (на сервер не выкладывается)
```

**Почему `app/` внутри webroot.** На хостинге Timeweb PHP заперт в пределах
корня сайта: файлы выше `public_html` он видит, но открыть не может (`fopen`
возвращает Permission denied даже для файлов владельца). Поэтому служебные
каталоги перенесены внутрь и закрыты двумя независимыми правилами: собственный
`app/.htaccess` с `Require all denied` и `RewriteRule ^app/ - [F,L]` в корневом
`.htaccess`. Это прямо предусмотренный CLAUDE.md запасной вариант. Проверено:
`/app/`, `/app/.env`, `/app/data/bookings.db` отдают 403.

## Локальный запуск

Нужен PHP 8.x (pdo_sqlite, curl, mbstring). Установка на Windows:
`winget install PHP.PHP.8.4`.

```bash
php -S localhost:8000 -t public_html
```

База и схема создаются автоматически при первом запросе
(или вручную: `php public_html/app/scripts/init_db.php`).

### Служба вместо cron (работает сейчас)

`crontab` по SSH на этом хостинге отключён — планировщик редактируется только
через панель. Поэтому его работу берёт на себя постоянная служба
`app/scripts/bot_daemon.php`: непрерывно опрашивает Telegram, раз в 5 минут
шлёт напоминания и досылает очереди, раз в час запускает `cleanup.php`.

| Действие | Команда |
|---|---|
| Запустить / перезапустить | `bash ~/public_html/app/scripts/bot_start.sh` |
| Проверить состояние | `php ~/public_html/app/scripts/bot_status.php` |
| Остановить | `touch ~/public_html/app/data/bot_daemon.stop` |

Служба переживает выход из SSH, но **не переживёт перезагрузку сервера** и
может быть остановлена хостингом. Надёжный вариант — задачи в планировщике
панели; со службой они уживаются благодаря файловым блокировкам.

### Cron в панели Timeweb — три задачи



Каждую минуту: опрос Telegram, чтобы бот отвечал на кнопки. Каждый запуск
держит длинный опрос около 55 секунд, поэтому ответы приходят практически
сразу; повторные запуски отсекаются файловой блокировкой.

```text
php /home/c/cc250576/public_html/app/scripts/bot_poll.php
```

Каждые 5 минут: напоминания о ближайших сессиях и досылка уведомлений,
не ушедших с первого раза.

```text
php /home/c/cc250576/public_html/app/scripts/flush_queues.php
```

Раз в час: удаление заявок старше RETENTION_MONTHS, чистка счётчиков,
продление горизонта слотов.

```text
php /home/c/cc250576/public_html/app/scripts/cleanup.php
```

## Telegram-бот

Служебный бот менеджера: дублирует уведомления о заявках, напоминает о
сессиях за `REMINDER_HOURS_BEFORE` часов и по кнопкам показывает записи
на сегодня, завтра, неделю и остаток свободного времени.

**Персональные данные бот не передаёт.** Telegram — зарубежный сервис,
поэтому в сообщениях только номер заявки, дата, время и статус; имя и
телефон открываются в админке по ссылке. Это требование CLAUDE.md п. 2.1
и текста согласия, где заявлено об отсутствии трансграничной передачи.

**Устройство: опрос, а не webhook.** Сеть Telegram с этого хостинга
фильтруется в обе стороны. Наши исходящие запросы проходят через часть
IP-адресов (перебор в `telegram_request()`), а вот доставить обновление к нам
Telegram не может — на webhook он получает «Connection timed out». Поэтому
инициативу берёт на себя сервер: `app/scripts/bot_poll.php` по cron раз в
минуту держит длинный опрос `getUpdates` около 55 секунд и отвечает на
сообщения. Файловая блокировка не даёт двум опросам работать одновременно,
смещение `update_id` хранится в `app/data/tg_offset.txt`.

Webhook-приёмник `public_html/api/telegram.php` оставлен как запасной путь на
случай переезда на площадку с доступной сетью Telegram — тогда достаточно
выполнить `setup_webhook.php`. Одновременно включать оба способа нельзя:
при установленном webhook Telegram перестаёт отдавать `getUpdates`.

Первичная привязка: пока `TELEGRAM_CHAT_ID` пуст, первый отправивший `/start`
становится чатом менеджера, и его идентификатор записывается в `.env`.
Дальше бот игнорирует всех остальных, отвечая им только ссылкой на запись.

Исходящие сообщения (уведомления и напоминания) идут через очередь на диске
с перебором IP-адресов Telegram: часть адресов с этого хостинга
отфильтрована, а IPv6 не отвечает вовсе, поэтому запросы принудительно
идут по IPv4, а не доставленное ждёт в `app/data/tg_queue/` и уходит
следующим проходом cron.

**Почему запоминается адрес.** Замеры с сервера: 149.154.167.220 отвечает
6 раз из 6 за 0,15 с, а 149.154.166.110 — 1 раз из 6, причём неудачи виснут
на стадии установки соединения (пакеты отбрасываются молча). DNS выдаёт как
раз второй, поэтому без памяти каждый запрос начинался бы с ожидания
таймаута: замер показывал 8,17 с на одно сообщение. Удачный адрес
сохраняется в `app/data/tg_endpoint.txt` и пробуется первым, таймаут на
соединение снижен до 2–3 с. После правки отправка занимает 0,15–0,25 с.
Память самовосстанавливающаяся: если сохранённый адрес перестанет отвечать,
перебор дойдёт до рабочего и запишет уже его.

## Чек-лист ручной проверки

1. **Бронирование**: выбрать час на `/booking/` → «Заявка принята», заявка в админке.
2. **Согласие**: без галочки кнопка неактивна; POST без `consent=1` → 400.
3. **Honeypot**: заполненное скрытое поле `website` → ответ «успех», заявки нет.
4. **Гонка слотов**: две брони одного слота → вторая получает 409.
5. **Лимит IP**: 4-я заявка за час с одного адреса → 429.
6. **Сбой почты/Telegram**: бронь создаётся, ошибка в `app/data/logs/app.log`,
   письмо уходит в `app/data/mail_queue/` и досылается кроном.
7. **Экран 360 px**: без горизонтальной прокрутки, кнопки от 44 px.
8. **Cookie-баннер**: до «Принять» запросов к `mc.yandex.ru` нет.
9. **Служебный каталог**: `/app/.env` и `/app/data/bookings.db` → 403.
